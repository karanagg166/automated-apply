# Phase 6B operations

Code, environment readiness and a real pilot are three independent outcomes. Configuration
checks make no connections and never label a populated credential as live verified. Runtime
reports under `reports/` are ignored by Git; JSON and Markdown are written atomically with
0600 permissions. They can contain public job evidence and private preference-derived scores;
retain them locally, restrict access, and remove them according to your retention policy.

## Commands from repository root

```sh
uv venv --python 3.11 backend/venv
uv pip install --python backend/venv/bin/python -r backend/requirements.txt
backend/venv/bin/python backend/scripts/check_environment.py
backend/venv/bin/python backend/scripts/migration_preflight.py
backend/venv/bin/python backend/scripts/smoke_test.py --mode local-offline
```

Exit 0 means that command's limited scope passed; exit 2 means configuration, authorization,
readiness or a provider outcome needs attention; exit 3 means execution failed. Zero companies
and partial discovery stay visible. An offline smoke success never implies deployment or live
Gemini success. `configured_not_verified` exit 0 from configuration inspection is explicitly
not database readiness. Invalid configuration errors name fields without echoing their values.

Operator scripts load **only** process environment and the file explicitly passed with
`--env-file`. The application retains its existing `.env` loading for compatibility. Do not
mount a developer `.env` into staging. Inherited shell variables take precedence over files;
use a clean operator environment and staging-only secret injection. No operation automatically
connects to a production database. Production inspection is configuration-only in these CLIs.

Staging database commands require `ENVIRONMENT=staging`, schema `job_agent`, a password-independent
`STAGING_DATABASE_ID`, and the same `--confirm-staging-target` value. The fingerprint covers the
host, effective port, database and schema, not credentials. DSN query overrides are rejected.
A fingerprint prevents accidental substitution; it cannot determine ownership or whether a
mislabelled database contains production data. Independently verify isolation before pinning it.

## Migration evidence

Migrations 001–009 contain no durable version ledger. Preflight compares actual PostgreSQL 16
catalogs with a reference generated by executing all ten (001–010) in a new disposable database. It
compares columns/defaults, indexes, validated constraints, trigger definitions/enabled state,
function definitions, RLS flags, policies, service_role grants and effective client/PUBLIC table
privileges. Missing/drifting objects mean `inconsistent_or_partial`. It never reports a historical
migration as applied merely because its tables exist. Extra policies fail inspection.

```sh
backend/venv/bin/python backend/scripts/migration_preflight.py \
  --env-file staging.private.env --inspect --confirm-staging-target "$STAGING_DATABASE_ID"
```

Inspection uses an actual `READ ONLY` transaction, bounded connection/statement timeouts and
catalog SELECTs. Dry-run/offline plan never connects or executes DDL. Keep migration files in
numerical order. Partial schemas need individual DBA review; blindly replaying all migrations
is not a repair procedure. Phase 7 added migration 010 and updated the catalog reference.

docker run -d --name automated-apply-phase6b-test-db \

The test password is fictional and confined to a loopback disposable container. Each verifier
creates/removes a uniquely named database; application/public schema preservation, budgets,
OAuth constraints, packet invariants, suppression and concurrency remain covered by existing
verifiers. `--write-manifest` regenerates the reference **only** on this disposable target;
review its diff and all ten migration hashes. CI checks the committed reference without rewriting it.

## Operator onboarding

Copy [the empty input template](profile-input.template.json) to `candidate.private.json`, chmod
0600, and fill it with owner-confirmed facts. Null identity fields intentionally fail validation.
Do not fill missing facts from guesses. Zero experience is an explicit assertion; an empty
work history with unknown experience stays unresolved. Project contribution and technologies,
role/location preferences, confirmed resume and professional links are checked. Link syntax
and declared facts do not constitute independent identity, employment or resume-byte verification.
No resume is downloaded or uploaded by this tooling.

```sh
backend/venv/bin/python backend/scripts/onboard_profile.py candidate.private.json
# Separate owner action; creates only if no profile exists (expected version 0).
backend/venv/bin/python backend/scripts/onboard_profile.py candidate.private.json \
  --env-file staging.private.env --apply --owner-confirmed --expected-version 0 \
  --base-url https://YOUR-STAGING-HOST --confirm-staging-target "$STAGING_DATABASE_ID"
```

The command reuses GET/PUT `/api/v1/profile`, checks the current version, supplies If-Match for
updates and relies on existing atomic compare-and-swap/idempotency. Use the actual current
version on subsequent updates; identical input preserves it. No private profile is printed.
Live profile APIs and the operator import reject common placeholder markers; this is a guard,
not a substitute for the owner's factual confirmation.

Save a confirmed resume with existing POST `/api/v1/candidate/resources` using a private JSON
file containing resource_type `resume`, label, public HTTPS URL, is_primary true and
user_confirmed true. First GET `/api/v1/candidate/resources` to resolve existing alternatives;
update by its saved id instead of adding a duplicate. Standard GitHub/LinkedIn/portfolio links
remain on the profile and require expected_profile_version when changed through resource APIs.
Confirmed project evidence can also be supplied through existing candidate evidence APIs.
Keep bearer headers in a 0600 `headers.private.txt` file, not shell history:

```sh
# File content: Authorization: Bearer <owner's staging API token>
curl --fail --silent --show-error --header @headers.private.txt \
  --header 'Content-Type: application/json' --data-binary @resume.private.json \
  --output /dev/null https://YOUR-STAGING-HOST/api/v1/candidate/resources
```

## Observability and failure response

`/health` is process liveness. `/ready` makes bounded database reads, checks required tables and
runtime SELECT permissions in live environments, and returns 503 with a fixed error if unavailable.
`GET /api/v1/operations/status` requires the owner bearer and returns sanitized persisted provider
states, profile gaps, Gmail identity/scopes/key usability, usage totals, source freshness, discovery
failures, rate limits, job/company counts and stale observations. It does not refresh OAuth,
reserve credits, call providers or repair migrations. Run catalog preflight separately for full
drift inspection. Optional providers do not gate process health. Gemini's existing concurrency
limit is per process; use one worker for this single-owner staging deployment.

For 429, wait for persisted cooldown/next_allowed_at; never clear counters. For timeout/5xx,
inspect durable run/check errors, then allow pacing before a new owner action. Same idempotency
key returns the prior run; an expired running lease becomes recovery_required, never automatic
provider replay. Interrupted paid reservations remain reserved until reconciled against provider
receipts. Disable an unavailable optional provider rather than restarting to erase its ledger.
No raw OAuth callback queries, prompt bodies, resumes or provider responses belong in logs.
