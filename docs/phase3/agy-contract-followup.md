# Phase 3 frontend contract follow-up

The original AGY delivery at `2a87789` is preserved. This follow-up is implemented by Codex on a separate linked branch after owner-approved Phase 2 merge `ec5dc9b`. It resolves the frontend contract audit recorded in [issue #38](https://github.com/karanagg166/automated-apply/issues/38).

Apify now displays actual backend source and Actor identities, local reservation accounting, and observed metadata. The fabricated Actor catalog, prices, verified rights, fallback budget, and chargeable dispatch controls are removed. Account and Actor inspectors use the exact owner-only metadata endpoints. A configured token or metadata response cannot authorize collection. LinkedIn collection and account rotation remain unavailable.

Read-only Gmail renders `account_email`, actual account states and permissions, and `schema_ready:false` setup state. The proxy forwards the new account OAuth browser-binding cookie. Evidence uses actual retained string links, timestamps, message/thread IDs, signals, and originating account. Raw sender/subject/body, inferred vacancy titles, and fabricated extraction status are not displayed. Account-scoped leads can be imported only after the owner inspects the posting, supplies its actual title, and confirms review. Gmail send, modify, archive, delete, drafts, and arbitrary operation routes remain outside the allowlist.

The missing-answer queue uses generated response types, effective stale status, exact saved versions, and a separate factual approval. Editing answer/evidence clears factual confirmation and disables approval until the changed draft is saved. The extension's existing `/profile?missing_input={id}` link opens the exact protected saved question, even if it is outside the first list page. Broader semantic reuse requires the separate reuse-approval API.

Candidate facts handle actual 409 conflicts and retain compatibility with 412 responses without labelling every conflict 412. The saved-drafts endpoint is an array; drafts and exact-context reviews are distinguished from separately approved broader reuse. Project/link changes require explicit truthful confirmation, and removing the last project can be persisted. Startup filters use `industries`, `country`, and `has_technical_staff`. Exact size badges require verified size evidence; technical staff badges use retained staff evidence, not a technology-stack guess. Contact cards distinguish published business-email sources, provider reports, authorized mailbox verification, and suppression/staleness. A confirmed resume selection does not claim PDF verification.

Validation is performed under `/tmp/automated-apply-heavy-tests.lock`. The first unit run returned 163 passed and two failed expectations: text matching for a source name and a fixture incorrectly expecting an exact headcount despite conflicting evidence. Those assertions were corrected to conservative real API behavior. Additional dirty-approval, actual profile-conflict, project-confirmation, and published-email regression cases were added. TypeScript and generated API response contracts compile. Full final suite totals and browser results are recorded by the integration report after the shared-lock runs finish.

`playwright.phase3.config.ts` runs the existing browser scenarios and three new cross-component journeys against actual FastAPI, disposable PostgreSQL, and the authenticated production frontend. Provider transport is explicitly intercepted. These fixtures prove application behavior, not genuine provider authorization or human physical toolbar gestures. The scenarios cover persisted unknown questions, frontend editing and exact approval/reuse; two mailbox evidence isolation, reviewed imports, denied writes and GET-only audit; actual profile 409 conflicts and stale approval invalidation. No real email, paid execution, employer submission, hosted CI, deployment, or live schema migration is performed.
