## Pending executor contract

Use `DISCOVERED → MATCHED → ELIGIBLE → PREPARING → READY_TO_APPLY → APPLYING →
QUESTIONS → RESUME_ATTACHMENT → VERIFYING → SUBMITTED_RECORDED`, allowing observed
variants to skip inapplicable question/upload stages. These are the required next
executor stages, **not states implemented by this milestone**. Existing execution
and packet lifecycle names remain compatible until that implementation is reviewed.

`NEEDS_INPUT` pauses one job for an unknown fact; native chooser dependency adds
reason `NEEDS_HUMAN`. `BLOCKED_PLATFORM` prevents site execution while permission
is missing or revoked. `PAUSED` fences owner/global controls. Use
`FAILED_RETRYABLE` only before any uncertain submitting effect, `FAILED_FINAL`
for known terminal failures, and `SUBMISSION_UNKNOWN` after an uncertain Apply,
answer continuation or upload selection. Global Stop also fences pending work.

Before each potentially submitting operation, transactionally recheck the standing
policy, platform grant, daily reservation, exact attempt/requisition, current
profile/resume/answer revisions, cancellation fence, command lease and
profile/window/tab/document/session binding. Commit admission before dispatch.
Lease expiry, Stop, restart or navigation after admission must never replay it.
Read-only permitted provider reconciliation is required before any later action.
Unknown outcomes remain unknown even if generic packet counters are zero.

Recognize direct application, pre-questions, resume requests, already-applied,
external employer redirects, further factual questions, validation errors, upload
failures and persistent provider confirmation separately. External redirects are
unsupported in this Naukri-only phase and must stop for review. A success page or
HTTP 200 alone cannot produce `SUBMITTED_RECORDED`. Exact persistent Application
Status establishes the Naukri record; employer acknowledgment and later recruiter
events are independent evidence. Notification delivery uses the existing
transactional outbox after durable state changes.

The standing policy must separately pin source scope, current preferences,
canonical resume, employer exclusions, supported application types, answer-source
revisions, submission cap, owner submission authority and validity, provider
permission evidence, notifications and Start/Pause/Stop. The existing policy is
preparation-only and cannot substitute for that submission grant.
